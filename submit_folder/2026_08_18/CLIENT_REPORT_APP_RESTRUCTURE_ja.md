## 1. 背景と要件

### 1.1. 背景

eGWアプリ（**Eminel**）は、既存アプリ **`syp-eminelstandard-app`**（以下 **E-Smart** と呼称、現在のapplicationId `jp.co.hokkaido-gas.esta`）と同一リポジトリで開発・格納される予定です。同一リポジトリに同居させる理由：

- 2つのアプリ間で **共通コンポーネントを再利用**したい：UIコンポーネント、ログイン機構、E-Smartとの共通ロジック。
- **アプリストアの掲載が別々**であるため（E-SmartとEminelはストア上で別アプリ）、同一リポジトリから**それぞれ個別にビルド**できる必要がある。

### 1.2. 達成すべきゴール

| # | ゴール | 説明 |
|---|---|---|
| 1 | **アプリ層**と**共通層**に分離し、1つのリポジトリで複数アプリを管理できること | 今後の開発フェーズで**コードを追加しやすい構成**であること |
| 2 | **E-Smart**と**Eminel**をそれぞれ独立したアプリとしてビルドできること | 異なる`applicationId`/bundle id、異なるストア配布パッケージ |
| 3 | Eminel側にコードを追加しても、E-Smartの開発に**影響を与えない**こと | 逆方向も同様 — 一方のアプリの変更がもう一方のリリースを必要としない |

### 1.3. スケジュール上の制約

| フェーズ | 内容 | 期限 |
|---|---|---|
| 1 | 変更後のディレクトリ構成の提案（SYP） | 8/3 – 8/14 |
| 2 | muiレビュー（mui, SYP） | 8/17 – 8/19 |
| 2a | レビュー結果の反映 | 8/20 – 8/21 |
| 3 | 実装（SYP） | 8/24 – 8/28週 |

本ドキュメントは **ステップ1** に対応するものです。

## 2. アプローチ方法と参考情報源

mui Lab社内の技術標準に沿った方案とするため（未検証の一般的なアーキテクチャを当てはめるのではなく）、以下3つの情報源を優先順位順に調査しました：

### 2.1. 参考リポジトリ：`kurashi-for-energy`

これは要件ドキュメント内で**mui Labが直接指定**したリポジトリです（「参考: 同様の構成」）。mui Labの別のエネルギー系アプリの実際に本番稼働中のソースコードであり、さらに重要な点として、リポジトリ内に**強制ルール形式の社内アーキテクチャドキュメント**（アーキテクチャ、ルーティング、ストレージ、デザインシステム、エラーハンドリング）が存在します。これはmui Labチーム自身が策定し実際に運用している標準であるため、`syp-eminelstandard-app`の再設計における**最も信頼度の高い参考情報源**と位置付けています。

**得られた結論：**
- ドメイン/ビジネスロジック全体を共通パッケージに切り出す必要はない — **実際に共通利用され、UIを持たない部分のみ**を共通パッケージへ。各アプリ固有のドメインはそのアプリ内に残す。
- 複数アプリ/ブランドを区別する仕組みは**アプリごとのフォルダ分離**であり、Gradle flavorは使用しない。
- ルーティング、Dependency Injection、デザインシステムに関する強制ルールが存在し、レビューを円滑にするためどのアーキテクチャ変更もこれに従うべき。

### 2.2. Eminelアプリの詳細機能要件ドキュメント

開発予定のEminelアプリに関する23件の機能要件ドキュメント（Aグループ：アカウント/ポイント/バッジ、Bグループ：Gateway経由の機器制御、Cグループ：エネルギーグラフ/レポート、Dグループ：お知らせ/アンケート/見守り、Eグループ：システムエラー/ログ/サポート/非機能要件）。

**得られた結論：** これは「どの機能を共通化すべきか、どの機能を分離すべきか」を正確に判断するための**決定的な情報源**です。画面名からの推測ではなく、ドキュメント内の直接的な記載（例：ある機能について「E-Smartに既に存在するため新規要件なし」、逆に「対象機器・通信方式がE-Smartと全く異なる」等）に基づいています。詳細な分類は4章・5.3節を参照。

### 2.3. `syp-eminelstandard-app`の既存ソースコード調査

`lib/`の構造、Android/iOS設定、Firebase設定、現行CI/CDフローを直接調査し、変更範囲を評価するための現状把握を行いました（詳細は4.1節）。

## 3. 方針を導く基準・ルール

本提案における全てのアーキテクチャ上の意思決定は、以下4つの基準グループのいずれかに基づいています：

### 3.1. お客様要件から生じる必須制約

- 共通/E-Smart/Eminelのモジュール分離は、最終的に1つのバイナリでビルドするか2つでビルドするかと**独立**している。
- **実際に異なる2つのアプリ**としてビルドできること（applicationId、ストア掲載が異なる）。
- 一方のアプリの変更が、もう一方の**リリースを必要としない**こと。
- 今後の機能・ブランド追加に対して**拡張しやすい**構成であること。

### 3.2. `kurashi-for-energy`基準による技術的必須ルール

| ルール | 内容 |
|---|---|
| ドメインロジック | 全体を共通パッケージに強制的に分離しない — 実際にheadless（UIなし）かつ真に共通利用される部分のみ分離 |
| Dependency Injection | 抽象的なproviderを1箇所に集約定義し、各アプリが起動時に具体的な実装をoverrideする；providerを各所に分散定義しない |
| ルーティング | `go_router`の使用を必須とし、`Navigator.push`による直接遷移を禁止；各画面はroute pathを明示的に宣言する — **新規アプリに適用**；既存アプリは、即時移行が不要なリスクを生む場合は現行方式を維持可能（5.4節参照） |
| デザインシステム | 色・余白の「ハードコード」を禁止し、デザイントークンの使用を必須とする；アプリ/ブランドが2つ以上になる場合、各アプリが独自の値セットを提供できるようトークンを抽象化する |
| コード内でのアプリ/ブランド判定 | UI内で「もしアプリAなら…」という分岐を禁止 — アプリ間の差異はinjection/theme機構で処理し、widget内で分岐しない |
| Android ビルド | ブランド区別にGradle flavorを使用しない — 各アプリを個別サブディレクトリとし、applicationIdはアプリごとに固定 |
| CI/CD | パイプラインはビルド/デプロイ対象アプリを選択するパラメータを持ち、認証情報（secrets）はアプリごとに分離する |
| workspace管理 | 複数パッケージからなるリポジトリ（monorepo）はglobパターン方式のworkspace管理ツールで宣言する |

### 3.3. 「共通 / E-Smart専用 / Eminel専用」機能の分類基準

1. 画面名からの推測より、**要件ドキュメント内の直接的な根拠**を優先する。
2. 2つのアプリが**同一のデータソース/バックエンドを使用**する場合（同一の記録システム、同一API）→ アプリごとに画面表示が異なっていても**共通**に分類する（例：ポイント）。
3. **通信方式やデータソースが全く異なる**場合、機能名が似ていても → **アプリごとに分離**し、無理に統合しない（例：automation/dr/sensor — 名前は似ているがデータ経路が全く異なる）。
4. ドキュメントが**分類判断に十分でない**場合 → お客様への追加確認リスト（7章）に入れ、勝手に推測して決定しない。

### 3.4. 実装時のリスク管理原則

- 実際にストアで公開中のアプリの識別子（`applicationId`/bundle id）を変更しない。
- 共通利用の境界が確定していない部分については、最初から細かく分割するのではなく、**現状構造を維持したまま一括で移動**することを優先し、不要なリスク・工数を削減する。
- 標準パッケージ化は**段階的に実施**してよく、初回実装で境界を100%完成させる必要はない。

## 4. アーキテクチャ選定の分析と根拠

### 4.1. `syp-eminelstandard-app`の現状ソースコード

| 観点 | 現状 |
|---|---|
| 規模 | 手書きのDartファイル481個・約74,000行（コード自動生成後は881ファイル。自動生成ファイルはリポジトリに未コミット） |
| 構造 | **レイヤー単位**（`data/`、`domain/`、`presentation/`、`server/`）— feature単位ではなく、複数画面をまたいで使用されるファイルが多数 |
| 画面遷移 | 旧方式の画面遷移（1ファイルに集約されたroute一覧、約30画面）、`go_router`未使用 |
| ビルド | Android/iOSプロジェクトは1つのみ、アプリ識別子（applicationId）はビルド時に動的に渡される、マルチアプリ/マルチブランドビルドの仕組み未整備 |
| テスト | 自動テスト（unit/widget/integration）は未整備 |
| 複数メーカー機器連携 | 実行時パラメータで処理、メーカーごとのモジュール分離なし |
| Eminel機能 | 現行ソースコードには**存在しない** — 全て新規開発 |

### 4.2. 検討したアーキテクチャの方向性

最終方針を決定する前に、パッケージ分離について2つの方向性を評価しました：

| 方向性 | 説明 | 評価 |
|---|---|---|
| **A — 機能ごとの細粒度パッケージ分離** | 各機能（E-Smart専用機能も含む）を独立したDartパッケージとする | 理論上は最も境界が明確だが、現在複数画面をまたいで使用されている`domain`/`data`レイヤー全体を分離する必要があり、工数・リスクが高く、feature単位の境界が未整備な現状のコードに適さない。また、`kurashi-for-energy`が採用する**実際の標準とも異なる**。 |
| **B — 真に共通な範囲のみを最小限に分離（`kurashi-for-energy`基準）** | 実際に共通利用されるものだけ（theme、UIコンポーネント、ユーティリティ、一部headlessドメイン）を共通パッケージへ分離；それ以外は各アプリ内にそのまま残す | 現状コードに適合（境界誤分離のリスクを低減）、mui Labが実際に運用している技術標準に一致、工数も大幅に低い |

**結論：** **方向性B**を採用します。理由は、1.2節の3つのゴールを満たしつつ、技術的リスクを最小化し、mui Lab社内標準にも合致するためです。

### 4.3. 具体的な機能分類のための分析

Eminelの機能要件ドキュメントとE-Smartの既存機能グループを照合し、直接的な根拠に基づく結論を導きました（要件ドキュメントの記載を引用）：

| 機能 | 分類 | 根拠 |
|---|---|---|
| ログイン／アカウント | **共通** | Eminel要件ドキュメントで確認：ログイン関連要件は全て「E-Smartに既に存在、新規要件なし」— 現行の認証機構をそのまま共用 |
| お知らせ／アンケート／プッシュ通知 | **共通** | Eminel要件ドキュメントで確認：「全要件がE-Smart既存のため新規なし」— 現行バックエンドシステムをそのまま再利用 |
| ポイント／バッジ・ランク | **共通** | E-Smartと共通の外部ポイント記録台帳（ledger）を使用、アプリごとに異なるのはポイント獲得経路のみ |
| スケジュール運転、温湿度センサー、在宅監視（E-Smartに既存） | **E-Smart専用** | Eminel要件ドキュメントで、対応するEminel側機能は**全く異なる仕組み**（通信方式・データソースが異なる）であると確認 — 再利用せず、E-Smart側にそのまま残す |
| Gateway経由の機器登録／制御、スマートメーター登録 | **Eminel専用** | Eminel要件ドキュメントで確認：対象機器・通信方式がE-Smartと完全に異なる（Gateway専用プロトコル）、完全新規開発 |
| エネルギーグラフ／レポート、センサー状況、省エネアドバイス | **Eminel専用** | データソース（スマートメーター、Gateway経由センサー）が現行E-Smartのデータと全く異なる |
| 見守り（人感センサーによる在宅監視） | **Eminel専用** | 旧世代Eminelアプリからの継承機能、E-Smartに相当機能なし |
| 設定（お客さま情報・通知設定） | **共通** | Eminel要件ドキュメントに「**全要件が現行・ESTAのいずれかに存在するため新規なし**」と明記 — 現行の仕組みをそのまま共用する。通知設定はプッシュ通知（共通）と表裏一体 |
| ヘルプ（操作ガイド・FAQ・利用案内） | **共通** | 同じく「現行・ESTAのいずれにも存在、新規なし」。参考リポジトリ`kurashi-for-energy`でも`packages/features/common`にFAQ・問い合わせが配置されており、社内標準と一致 |
| アプリログの収集・送信 | **共通（画面なし）** | 「現行・ESTAのいずれにも存在、新規なし」。ユーザーが操作する画面を持たないため、機能パッケージではなく**共通基盤**（`packages/utils`＋送信APIは`packages/data`）に配置するのが適切 |
| システムエラー表示 | **表示部品は共通／データ経路はアプリ別** | エラーの発生元・取得経路が両アプリで全く異なる（EminelはGateway管理クラウド経由、E-Smartは現行の機器エラー）。一方、参考リポジトリには`packages/ui_components`にエラー表示部品が存在するため、**表示部のみ**共通化する |
| DR | **今回のディレクトリ設計では枠のみ確保** | Eminel側のDRは要件ドキュメント上「**26年対応スコープ＝なし**」であり本フェーズの実装対象外。E-Smartの既存DR画面は`apps/e-smart-app`にそのまま残す |
| 非機能要件 | **分類対象外（横断制約）** | 画面を持つ機能ではなく、両アプリ・共通パッケージ全体に適用される制約であるため、ディレクトリ分類の対象としない |

**ネットワーク基盤に関する重要な発見：** Eminelの非機能要件ドキュメントにより、Gateway機器のデータ通信経路は**専用チャネル（Gateway管理クラウド経由のMQTTプロトコル）**であり、E-Smart現行のREST APIチャネルとは全く異なることを確認しました。そのため、本提案における「共通ネットワーキング」は**実際に共通利用されるREST APIのみ**（ログイン、お知らせ、ポイント等）に限定すべきであり、Gateway通信レイヤーはEminel専用の基盤として扱います。

## 5. 提案するソリューション

### 5.1. 全体アーキテクチャ

**モノレポ**モデルとし、**アプリ層**（`apps/`）と**共通層**（`packages/`）の2層構成とします。

```
                  packages/
   (theme, ui_components, utils, data, features/common)
    — 共通層、どのアプリにも依存しない —
                 │                    │
                 ▼                    ▼
     apps/e-smart-app        apps/e-gw-app
   （既存アプリ、             （新規アプリ、
    固有ロジックを維持）        Eminel固有ロジック）
```

**中核原則：** 共通パッケージは**アプリに逆依存しない**；各アプリは自身のニーズに応じて共通パッケージの利用方法を自ら決定する。2つのアプリは**互いに依存しない**。

### 5.2. 詳細ディレクトリ構成

```
syp-eminelstandard-app/
├── apps/
│   ├── e-smart-app/                # 既存アプリ — 現状のまま移動
│   │   ├── android/ ios/          #   実際に公開中のapplicationIdを維持
│   │   └── lib/
│   │       ├── main.dart          #   E-Smart固有の実装を提供する初期化処理
│   │       ├── data/ domain/ presentation/ server/   # 現行構造を維持
│   │       └── router/            #   E-Smart専用の画面遷移テーブル
│   │
│   └── e-gw-app/                # 新規アプリ
│       ├── android/ ios/          #   新規applicationId、新規Firebase設定
│       └── lib/
│           ├── main.dart
│           ├── data/ domain/ presentation/ server/   # 新規機能開発の受け皿
│           └── router/
│
├── packages/
│   ├── theme/                     # 共通デザイン：色、タイポグラフィ、余白
│   ├── ui_components/             # 共通UIコンポーネント（エラー表示部品を含む）
│   ├── utils/                     # 共通ユーティリティ：ロギング、アプリログの収集・送信、
│   │                              #   ローカルストレージ、共通フォーマッタ等
│   ├── data/                      # 共通データ層：entities / datastores / repositories /
│   │                              #   RESTクライアント（参考リポジトリの外部データパッケージと
│   │                              #   同じ構成を、今回はリポジトリ内に配置）
│   └── features/
│       └── common/                # 共通ロジック（UIなし）：ログイン、設定（お客さま情報・通知設定）、
│                                  #   ポイント/バッジ、お知らせ/アンケート/プッシュ通知、
│                                  #   ヘルプ（操作ガイド・FAQ・利用案内）
│
└── （リポジトリルートのworkspace管理設定）
```

> `apps/e-smart-app`、`apps/e-gw-app`、`packages/`というディレクトリ名は、共有いただいた社内技術方針ドキュメントに基づき確認済みであり、共通層（`packages/`）とアプリ層（`apps/`）を分離し、各アプリが独自のtheme/配色を持つという方針とも一致しています。

**`packages/data`を別立てとする理由（参考リポジトリとの差分）：** 参考リポジトリ`kurashi-for-energy`では、データ層（repository実装・APIクライアント）を**リポジトリ外のデータパッケージ**に切り出しています。一方、`syp-eminelstandard-app`には相当する外部パッケージが存在せず、現行の`lib/data`・`lib/server`は参考データパッケージと**ほぼ同じ構成**（`server/mui_service.dart`・`mui_api_endpoint.dart`・`rest_client/`・`data/{entities,datastores}`）です。そのため本提案では、**同じ構成のままリポジトリ内の`packages/data`へ移動**する方針とします——2つのアプリが同一リポジトリにある現段階ではこれで共用目的を達成でき、将来外部パッケージ化が必要になった場合も**パッケージごと切り出すだけ**で済むためです。

### 5.3. 機能分類の全体表

| グループ | 新構成における配置 | 該当機能 |
|---|---|---|
| **共通（ロジック・画面なし）** | `packages/features/common` | ログイン/アカウント、**設定（お客さま情報・通知設定）**、お知らせ、アンケート、プッシュ通知、ポイント、バッジ/ランク、**ヘルプ（操作ガイド・FAQ・利用案内）** |
| **共通（UI・デザイン）** | `packages/theme` + `packages/ui_components` | デザイントークン、共通UIコンポーネント、**エラー表示部品**（システムエラーの表示部） |
| **共通（画面を持たない基盤）** | `packages/utils` | **アプリログの収集・送信**、ロギング、ローカルストレージ |
| **共通（データ層）** | `packages/data` | 両アプリが共用するRESTクライアントとその entities / datastores / repositories（ログイン・お知らせ・アンケート・ポイント・問い合わせ・アプリログ等） |
| **E-Smart専用** | `apps/e-smart-app`（現在の位置を維持） | 既存のスケジュール運転、複数メーカーのエアコン/給湯器連携、赤外線制御、E-Smart専用アンケート、既存のセンサー/監視画面、**既存のDR画面**、**既存の機器エラーのデータ経路** |
| **Eminel専用** | `apps/e-gw-app`（新規開発） | Gateway経由の機器登録/制御、スマートメーター登録、エネルギーグラフ/レポート、センサー状況、省エネアドバイス、見守り、**E-GW由来のエラー取得（システムエラーのデータ経路）** |

> **「共通」の範囲について（画面の再利用可否）：** 上表の「共通」は、**ロジック・状態管理・データ取得・UI部品**の共通化を指します。参考リポジトリの技術標準では`packages/features/common`は**画面を持たず**（UIフレームワークへの依存なし）、`packages/ui_components`はボタン・入力欄・リスト・モーダル等の**部品**を提供する層です。したがってログイン画面・お知らせ画面などは、**取得処理と状態管理は両アプリで共用しつつ、画面自体は各アプリ側で組み立てる**形になります。これは「アプリごとにtheme・配色を変えたい」というご要望と整合する構成であり、画面ファイルそのものを1つにまとめて2アプリで共有する方式は採用していません。


### 5.4. 適用する技術原則

- **画面遷移（ルーティング）：** アプリごとに異なる方式を適用 — **E-Smart既存アプリへの影響を最小化する**という基準を優先して決定済み：
  - `apps/e-smart-app`：**現行の画面遷移方式をそのまま維持**、ロジックを変更せず現状のまま移行 — 安定稼働中の遷移フローを壊すリスクを完全に排除。
  - `apps/e-gw-app`：最初から`go_router`を使用 — 完全新規アプリであるため後方互換性リスクがなく、新規コードに関する`kurashi-for-energy`の技術標準にも準拠。
  - これは意図的な例外であり、「対応漏れ」との誤解を避けるため技術ドキュメントに明記します；必要であれば後のフェーズで`e-smart-app`を`go_router`へ移行することも可能です。
- **Dependency Injection：** 共通利用のusecaseは共通パッケージ内で抽象的に宣言し、各アプリが起動時に具体的な実装を提供する — 必要に応じて同一ロジック箇所で2アプリが異なる挙動を持てる（例：ログイン後、各アプリが異なるメイン画面へ遷移）。
- **デザイン（デザインシステム）：** 本フェーズの時点でデザイントークンを抽象化した形で標準化する（2アプリ体制になる最初の機会のため）、各アプリが共通部分を壊さずに独自のUIをカスタマイズできるようにする。
- **UI内でアプリ別分岐をしない：** 2アプリ間の挙動差異は全て設定/injection機構で処理し、画面内で「どのアプリか」を直接判定する条件分岐は書かない。

### 5.7. 工数見積もり

調査済みのソースコード規模（4.1節）に基づく、上記フェーズ1〜5全体（Eminel側の新規ビジネス機能開発は含まない）の概算工数：エンジニア1名がフルタイムで対応した場合**約15〜27人日**。この見積もりには、`apps/e-smart-app`の画面遷移方式を現状維持とする決定（5.4節）を織り込み済みです — もしこの決定がなければ、既存の約30画面全てを再点検する必要があり、工数はさらに大きく増加します。

全体スケジュールにおける実装予定期間[8/24 – 8/28]（約5営業日）と比較すると差異があり、着手前に範囲・リソースについて協議が必要です（7章 質問5を参照）。

## 6. 留意すべき主要リスク

| # | リスク | 深刻度 | 軽減策 |
|---|---|---|---|
| 1 | E-Smart実運用アプリの識別子（applicationId）を誤って変更してしまう | **非常に高い** | ビルド設定変更前に、実際に稼働中の識別子を確認する |
| 2 | 自動テストが未整備のため、大量のソースコード移動時のリグレッションを早期に発見しづらい | 高い | リリース前に、現行画面一覧に基づく手動テストチェックリストを作成する |
| 3 | 同一リポジトリ内でE-SmartとEminelが異なる画面遷移方式を採用する（意図的な決定 — 5.4節） | 低い | 「対応漏れ」との誤解を避けるため技術ドキュメントに明記；必要であれば後フェーズで統一する計画を立てる |
| 4 | 見積もり工数と提示された実装スケジュールとの差異 | 中〜高 | 着手前にお客様と範囲/リソースについて再協議する |
| 5 | ソースコード以外の基盤項目（Firebase、keystore、ストアへのアプリ登録）は独自のリードタイムがあり、コード進捗に依存しない | 中程度 | レビュー段階から並行してこれらの基盤要件に着手し、コード完了を待たない |

## 7. お客様に確認いただきたい事項

| # | 確認事項 | 重要な理由 |
|---|---|---|
| 1 | `e-gw-app`の正式なapplicationId/bundle idの確認 | ビルド設定、Firebase、keystoreに直接影響 |
| 2 | **Android版**E-Smartの公開中applicationIdの確認（iOS側は`jp.co.hokkaido-gas.esta`であることをリポジトリ上で確認済み。Android側は`APP_ID`をビルド時に環境変数から渡す方式のため、リポジトリからは確認できません） | 設定変更時にストア上で新規アプリ扱いとなるリスクを回避するため |
| 3 | 実装期間[8/24 – 8/28]の範囲に、Eminelの新規ビジネス機能開発を含むか、それともディレクトリ再構成と空のアプリシェル構築のみか | 実際の工数とスケジュール達成可能性に大きく影響 |
| 4 | E-SmartとEminelアプリ間でシングルサインオン（SSO）が必要か | Eminel要件ドキュメントでは現時点で明確に確認されていない — ログイン機構の共通化範囲に影響 |
| 5 | Eminel用の新規基盤項目（Firebase project、App Store/Play Storeアプリレコード、keystore）を誰が構築するか、いつ着手するか | これらの項目は独自のリードタイムがあり、全体進捗を遅らせないために早期着手が必要 |
| 6 | Eminel機能要件ドキュメント自体に「未確定」と記載されている一部内容（例：システムログの保存先、一部の設定/省エネアドバイス画面の具体的な挙動、Gateway側データの更新頻度） | ビジネスロジックの詳細実装前に確定が必要（本フェーズのディレクトリ構成設定には影響しない） |
