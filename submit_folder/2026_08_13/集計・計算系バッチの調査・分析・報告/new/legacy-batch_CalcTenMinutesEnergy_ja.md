# 旧バッチ — CalcTenMinutesEnergyCommand（10分毎ガス使用量差分データ算出）

## 概要

`CalcTenMinutesEnergyCommand` は旧システム（EMINEL コンシェルジュサーバー）で1時間に6回実行されるバッチで、ガスメーターの積算カウンタ（設置されている場合はコジェネレーション／燃料電池も含む）を2回連続で読み取った差分から、各戸ごとに**直近10分間のガス使用量**を算出し、暖房用コントローラーの信号に基づく7分岐の決定木で**ガス合計／給湯／暖房**に推定分離する。結果は `s_101` テーブルに書き込まれる。クラス名は「Energy」だが、このバッチが処理するのは**ガスのみ**であり、電力消費・発電・売買電・蓄電池は対象外である。詳細はPart 2を参照。

## Part 1 — 概要

| 項目 | 内容 |
|---|---|
| **役割** | 各戸ごとに10分間のガス使用量を算出する（ガスメーター＋コジェネレーション／燃料電池）。合計／給湯／暖房への推定分離も行う。 |
| **Input** | 3つのDBテーブルから読み取る: `t_202`（ECHONET生データ — ガスメーターEPC `0xE0`、コジェネレーション／燃料電池EPC `0xC8`、暖房指令EPC `0xA0`）＋ `t_101`（契約／熱源マスタ）＋ `s_101`（前回の集計結果）。 |
| **Output** | DBテーブル `s_101` にInsertする — 分離対象の戸は10分枠ごとに3レコード（ガス合計・給湯・暖房）、分離対象外の戸はガス合計のみ1レコード（§2.6参照）。 |
| **処理概要** | 1. cronが1時間に6回実行され、マスタデータが揃っていて未処理の戸を選ぶ。<br>2. 4種類の異なるparseルール（ガスメーター／コジェネレーション／暖房指令）で生データを読み取る。<br>3. 単位を正規化し、差分を計算し、同一timestampの2つのガス源を加算する。<br>4. 閾値 `[0.0, 6.0]` でフィルタし、3日以内の欠損データを均等補完する。<br>5. 7分岐の決定木（暖房指令に基づく）でガス合計→給湯／暖房を分離し、`s_101` に3レコードを書き込む。 |

## Part 2 — 詳細

### 計算の全体図 — 8ステップ

このバッチの計算全体 — 生の16進文字列から結果レコードまで:

```
ステップ1  戸を選ぶ         → マスタデータが揃い、未処理の戸のみ抽出            §2.1
ステップ2  raw読み取り      → フィールド種別ごとに4つの異なるparseルール       §2.3
ステップ3  正規化           → hexdec(文字列) × 0.001  →  m³                    §2.4
ステップ4  差分計算         → 今回 − 前回；負の場合 → 0                        §2.4
ステップ5  2つの源を加算    → ガスメーター ＋ コジェネレーション（同timestamp） §2.4
ステップ6  閾値フィルタ     → [0.0, 6.0] 範囲外 → 0に強制                      §2.5
ステップ7  欠損補完         → 3日以内なら均等分配                              §2.5
ステップ8  暖房分離         → 決定木 → 7分岐のいずれか                         §2.6
           結果書き込み    → 3レコード: 合計／給湯／暖房                      §2.7
```

| ステップ | 内容 | 詳細箇所 |
|---|---|---|
| 1 | 戸の選定 — 2つのスキップ条件 | §2.1 · §2.2 |
| 2 | 生データ読み取り — **4つの異なるparseルール** | §2.3 |
| 3–5 | 単位正規化・差分計算・2つのガス源の加算 | §2.4 |
| 6–7 | 閾値フィルタ・欠損データ補完 | §2.5 |
| 8 | ガス合計／給湯／暖房の分離 — **7分岐の決定木** | §2.6 |
| — | 結果レコードの構造 | §2.7 |

> 具体的な数値で8ステップを手計算した例: §2.4の末尾。

### 2.1 実行条件と処理範囲

| 項目 | 内容 |
|---|---|
| デフォルトの基準時刻 | `現在時刻 − 40分`、その後10分単位に切り下げ |
| 再実行用パラメータ | `--datetime`、処理対象時刻を指定可能 |
| 処理単位 | EMS-SP（戸）単位 |
| rawデータソース | `t_202`（エンティティ `ConDeviceStatuses` 経由） |
| 前回処理の状態 | `s_101`（エンティティ `ConSensorMemoryValues` 経由） |
| 結果 | `s_101` 内の10分単位レコード |
| 結果種別 | `2` = ガス合計、`3` = 給湯、`4` = 暖房 |

このバッチは1つの10分枠だけを処理するわけではない。各戸について、直前の集計済みレコードを取得し、その次の時点から `targetDate + 20分` までのrawデータを読み取る。そのため1回の実行で**複数の未処理枠をまとめて補完する**ことがある。

#### 戸をスキップする2つの条件

戸ごとのループ内に2つの早期スキップ条件があり、**計算対象となる戸の範囲**に直接影響する:

| # | 条件 | 動作 | 意味 |
|---|---|---|---|
| 1 | `gas_contract_type` **または** `gas_cogeneration` **または** `water_heater_power` が空 | 戸を完全にスキップ | マスタデータが欠けていると計算できない |
| 2 | 直近の集計済みレコードが**すでに** `targetDate` と一致 | 戸をスキップ | この枠は既に処理済み — 重複計算防止の仕組み |

### 2.2 処理対象リストを作るSQL

最初のSQLは、論理削除されていない全顧客を取得し、`s_101` 内の直近のガス合計レコードを結合する:

```sql
SELECT customer.c001 AS ems_sp,
       customer.c021 AS gas_type,
       customer.c022 AS main_sensor_room,
       customer.c023 AS gas_contract_type,
       customer.c024 AS gas_cogeneration,
       customer.c043 AS water_heater_power,
       sensor.param,
       sensor.prev_kyutou_measured,
       sensor.prev_danbou_measured,
       sensor.date_time,
       CASE WHEN customer.c011 = 1
             AND customer.c023 = 1
             AND customer.c043 IN (1, 2, 4)
             AND customer.c043 = customer.c042
             AND customer.c043 <> customer.c044
             AND customer.c052 IS NULL
            THEN TRUE ELSE FALSE END AS separate_calc_target
  FROM t_101 AS customer
  LEFT JOIN (
        SELECT DISTINCT ON (sougou.c001)
               sougou.c001 AS ems_sp,
               sougou.c004 AS date_time,
               sougou.c007 AS param,
               kyutou.c006 AS prev_kyutou_measured,
               danbou.c006 AS prev_danbou_measured
          FROM s_101 AS sougou
          LEFT JOIN s_101 AS kyutou
            ON sougou.c001 = kyutou.c001
           AND kyutou.c002 = 3
           AND sougou.c004 = kyutou.c004
          LEFT JOIN s_101 AS danbou
            ON sougou.c001 = danbou.c001
           AND danbou.c002 = 4
           AND sougou.c004 = danbou.c004
         WHERE sougou.c004 <= :targetDate
           AND sougou.c002 = 2
         ORDER BY sougou.c001, sougou.c004 DESC
  ) AS sensor ON customer.c001 = sensor.ems_sp
 WHERE customer.c052 IS NULL
 ORDER BY customer.c001;
```

### 2.3 使用する生データ

#### Gas meter（ガスメーター）

| 条件 | 値 |
|---|---|
| ECHONET class/instance | `028201` — ガスメーター |
| EPC | `0xE0` — ガス積算 |
| 旧フィールド | `dev_epce0` |
| レコード種別 | `EA`, `EB` |

#### Cogeneration / fuel cell（コジェネレーション／燃料電池）

| 条件 | 値 |
|---|---|
| ECHONET class/instance | `027F01` または `027C01` |
| EPC | 旧ソースでは `dev_epcc8` から読み取るコード |
| 使用条件 | 契約設定でmy-home発電がある戸 |

#### Heating command（暖房指令）

| 条件 | 値 |
|---|---|
| ECHONET class | `0F4500`〜`0F45FF` |
| EPC | `0xA0` |
| 値の意味 | `0x00` = 指令なし、`0x3C` = 低温指令、`0x50` = 高温指令 |
| 読み取り範囲 | 現在の枠、10分・20分・30分前 |

#### ⚠️ 同じ `t_202` テーブル上の4つの異なるparseルール

このロジックを読む際に最も間違えやすい点。同じテーブル、同じ16進文字列形式でも、データ種別ごとに読み方が異なる:

| データ種別 | Field | 読み方 | 結果 |
|---|---|---|---|
| ガスメーター | `dev_epce0` | `hexdec(**文字列全体**) × 0.001` | m³ |
| コジェネレーション／燃料電池 | `dev_epcc8` | `hexdec(**文字列全体**) × 0.001` | m³ |
| 暖房指令 | `dev_epca0` | `hexdec(substr(文字列, **2, 2**))` — **2バイト目のみ** | `0` / `60` / `80` |
| *(参考)* 人感センサー | `c248` / `c249` | `hexdec(substr(文字列, **0, 8**))` — **先頭8文字** | 回数 |

```php
// ガス／コジェネレーション — 文字列全体を変換、単位係数あり
hexdec($value) * 0.001

// 暖房指令 — 2バイト目のみ、係数なし
hexdec(substr($heatingOrderTimes, 2, 2))
```

暖房指令については、文字列が空の場合は指令なしとみなす。旧バッチは**4種類すべてに共通の変換関数を使っていない**。

#### 2つのガス源の結合方法

バッチは `t_202` に対して**2つの別々のクエリ**を実行する:

| クエリ | フィルタ条件 | 取得フィールド |
|---|---|---|
| ① ガスメーター | `class_eoj = '028201'` | `dev_epce0` |
| ② コジェネレーション／燃料電池 | `class_eoj IN ('027C01', '027F01')` | `dev_epcc8` |

その後、**2つの結果をtimestampで結合**し、計測時刻が一致する場合のみ加算する。単一のJOINクエリではない。

> ソースでは燃料電池のフィールド名を `dev_epcc8`（つまりEPC `0xC8`）としているが、コード内のコメントには `EPC 0xE0` と書かれている。これは旧システムのコード自体に存在する不整合である。

### 2.4 10分間のガス使用量の計算式

16進の積算値を業務単位に変換する:

```text
measured = hexdec(raw) × 0.001
delta    = round(current_measured − previous_measured, 4)
delta < 0  → 0
raw null   → 0
```

コジェネレーション／燃料電池がある戸の場合:

```text
gas_10m = delta_gas_meter + delta_cogeneration
```

2つのデータ系列はtimestampが一致する場合のみ加算される。`record_period <= 0` のガスメーターレコードは除外される。

人感センサーのバッチと異なり、このバッチは**カウンタ一周分の補正を行わない**。リセット／機器交換／エラーで積算値が減った場合、結果は `0` に強制される。

#### 手計算の例

ガスメーター＋コジェネレーションがあり、熱源13A、暖房／給湯分離モードの戸の場合:

| ステップ | 値 |
|---|---|
| ガスメーター — 前回読み値 | `0001E240` → `123456 × 0.001` = **123.456 m³** |
| ガスメーター — 今回読み値 | `0001E250` → `123472 × 0.001` = **123.472 m³** |
| → ガスメーターの差分 | `round(123.472 − 123.456, 4)` = **`0.016`** |
| コジェネレーション — 前回 | `00002710` → `10000 × 0.001` = **10.000 m³** |
| コジェネレーション — 今回 | `00002716` → `10006 × 0.001` = **10.006 m³** |
| → コジェネレーションの差分 | **`0.006`** |
| **10分間のガス合計** | `0.016 + 0.006` = **`0.022`** |
| 閾値 `[0.0, 6.0]` の確認 | 範囲内 → そのまま |

その後、暖房／給湯分離の決定木（§2.6）に入る:

| 条件 | 想定値 | 結果 |
|---|---|---|
| `prev30MinOrderTimes` | `2`（> 0） | 上側の分岐へ |
| `highOrderTimes` | `0` | 低温指令の分岐へ |
| `lowOrderTimes` | `1`（> 0） | 低温側の閾値を判定 |
| `cost >= LOW_TEMP[13A]` | `0.022 >= 0.15` → **偽** | → **flag 3** |
| **flag 3の結果** | 暖房ガス = `0.022`、給湯ガス = `0` | |

`s_101` に**3レコード**を書き込む: 種別`2` = `0.022`、種別`4` = `0.022`、種別`3` = `0`。

### 2.5 欠損データの処理

| 2回の計測間の間隔 | 旧システムの処理 |
|---|---|
| ちょうど10分 | 10分値を1つ書き込む |
| `10分超` かつ `3日以内` | 差分を10分枠の数で均等分配し、小数点4桁で四捨五入 |
| `3日超` | 補完しない；前回の暖房ガスを`0`にリセット |
| ガス合計が`[0.0, 6.0]`の範囲外 | `0`に強制 |

```text
number_of_slots = round(period_minutes / 10)
value_per_slot  = round(total_delta / number_of_slots, 4)
```

均等分配のルールは旧システムの仕様上の挙動であり、実際の計測データではない。

### 2.6 ガス合計 → 給湯／暖房の分離

#### 解決すべき問題

各家庭には**ガスメーターが1つ**しかなく、**ガスの合計量**しか計測できない。暖房用・給湯用の個別メーターは存在しない。

しかしアプリでは**2種類を分けて表示したい**。どうすればよいか？

```
ガスメーターが言っているのは:  「直近10分でこの家は0.45 m³のガスを使った」

しかしアプリが必要としているのは:  「そのうち暖房はどれだけ？ 給湯はどれだけ？」
                   → 計測する方法は無い。推定するしかない。
```

> ⚠️ **これは推定アルゴリズムであり、計測ではない。** そのため複雑で分岐が多い。

#### 何を根拠に推定するか

旧システムは**暖房コントローラー**（暖房制御ユニット）を手がかりに使う。この機器は暖房が必要なときに**「暖房指令」**を発する:

| 手がかり | 何が分かるか |
|---|---|
| この枠に**暖房指令があるか** | 暖房が動いているかどうか |
| **直前3枠**に指令があったか | 暖房が継続運転中か、たった今ONになったか |
| 指令が**高温か低温か** | 暖房が強いか弱いか |
| ガス量が**多いか少ないか** | 少なすぎる場合は暖房のみで、入浴していないと推定 |

#### 4つの入力変数

| 変数 | 意味 | 値 |
|---|---|---|
| `prev30MinOrderTimes` | **直前3枠に暖房指令があったか** | `0`〜`3`（各枠0か1） |
| `highOrderTimes` / `lowOrderTimes` | **現在の枠**に高温／低温指令があるか | `0` または `1` |
| `cost` | 現在の枠の10分間ガス合計 | m³ |
| `prevHeatingThreshold` | **前日**の暖房平均レベル | m³（デフォルト `0.03`） |

> 各枠では暖房指令レコードを**1件しか**読まないため、これらの変数は実質的に**0/1のフラグ**であり、回数ではない。

#### 考え方: 2つの大きな状況に分ける

```
┌─ 状況A ────────────────────────────────────┐
│  直前3枠に暖房指令が**あった**               │
│  →  暖房は**安定運転中**                    │
│  →  ガスは暖房と給湯の両方に分配             │
└───────────────────────────────────────────┘

┌─ 状況B ────────────────────────────────────┐
│  直前3枠に暖房指令が**なかった**             │
│  →  今この時点で指令があれば**起動直後**     │
│  →  起動時は固定的に大量のガスを消費         │
└───────────────────────────────────────────┘
```

#### 決定木

```
prev30MinOrderTimes = 直前10分・20分・30分の3枠の暖房指令の合計

┌─ A. prev30MinOrderTimes > 0  ── 暖房は安定運転中
│
│   ├─ この枠に高温指令がある
│   │     ├─ cost >= 0.2   → 給湯にも余裕あり
│   │     │     ├─ 前枠が前日平均より多く使っていた  → flag 1
│   │     │     └─ そうでない場合                    → flag 2
│   │     └─ cost < 0.2    → 少なすぎる、暖房のみ     → flag 3
│   │
│   ├─ この枠に低温指令のみある
│   │     ├─ cost >= 0.15  → 給湯にも余裕あり
│   │     │     ├─ 前枠が前日平均より多く使っていた  → flag 1
│   │     │     └─ そうでない場合                    → flag 2
│   │     └─ cost < 0.15   → 少なすぎる、暖房のみ     → flag 3
│   │
│   └─ この枠に指令が全くない  → 暖房が停止した直後    → flag 4
│
└─ B. prev30MinOrderTimes = 0  ── 暖房は直前まで動いていなかった
    │
    ├─ この枠に暖房指令がある  → 起動直後
    │     ├─ cost >= 0.3  → 十分大きい、給湯分もある   → flag 5
    │     └─ cost < 0.3   → 起動分の暖房のみ          → flag 6
    │
    └─ この枠に指令がない → 暖房なし                   → flag 7
```

#### 7つの分岐 — 各分岐の意味

| Flag | どの場合に該当するか | 暖房ガス | 給湯ガス | 解釈 |
|---|---|---|---|---|
| **1** | 暖房が安定運転中、ガスが十分多い、**前枠が多く使っていた** | ＝ **前枠の暖房ガス** | 合計 − 暖房 | *「10分前と同じ暖房レベルを維持」* |
| **2** | 暖房が安定運転中、ガスが十分多い、**前枠が少なく使っていた** | ＝ **前日の平均値** | 合計 − 暖房 | *「前日の平均レベルを推定値として使用」* |
| **3** | 暖房は動いているが**ガスが少なすぎる** | ＝ **全量** | `0` | *「これだけ少ないなら誰も入浴していないはず」* |
| **4** | 30分前まで暖房があったが、**この枠は指令なし** | `0` | ＝ **全量** | *「暖房は止まった → ガスは給湯のもの」* |
| **5** | 暖房が**起動直後**、ガスが十分多い | ＝ **固定`2.0`** | 合計 − `2.0` | *「起動時は固定量のガスを消費する」* |
| **6** | 暖房が起動直後、**ガスが少ない** | ＝ **全量** | `0` | *「暖房の起動分だけで精一杯」* |
| **7** | **暖房指令が全くない** | `0` | ＝ **全量** | *「暖房なし → 全量が給湯」* |

#### 3つの具体例

| | 例①: 夜の入浴 | 例②: 暖房が今ついた | 例③: 暖房が安定運転中 |
|---|---|---|---|
| 直前3枠に指令があったか？ | なし（`0`） | なし（`0`） | あり（`2`） |
| この枠に指令があるか？ | なし | あり（高温） | あり（低温） |
| 10分間のガス合計 | `0.85` | `2.40` | `0.22` |
| → 分岐 | **flag 7** | **flag 5** | **flag 1 または 2** |
| **暖房ガス** | `0` | `2.0` | ＝ 前枠 ／ 前日平均 |
| **給湯ガス** | `0.85` | `0.40` | 残りの部分 |

#### 比較に使う3つの閾値 — 給湯熱源ごとの配列

| 定数 | 13A（`1`） | LPG（`2`） | 使用される分岐 |
|---|---|---|---|
| 高温指令の閾値 | `0.2` | `0.2` | A — 高温分岐 |
| 低温指令の閾値 | `0.15` | `0.15` | A — 低温分岐 |
| 起動閾値（`0.15 × 2.0`） | `0.3` | `0.3` | B — 起動分岐 |

現時点では2列の値が同じため計算結果に差は出ないが、データ構造は配列になっており、熱源ごとに個別の値を設定できる設計になっている。

#### 分離が許可される条件

すべての戸で分離するわけではない。`separate_calc_target = true` の場合のみ分離し、これは顧客マスタ上の**6つの条件を同時に満たす**必要がある:

| # | 条件 |
|---|---|
| 1 | 暖房制御モード ＝ 自動 |
| 2 | ガス契約種別 ＝ 規定の種別 |
| 3 | 給湯熱源 ∈ `{13A, LPG, 油}` |
| 4 | 給湯熱源 ＝ 暖房熱源 |
| 5 | 給湯熱源 ≠ 第三の熱源種別 |
| 6 | 論理削除されていない戸 |

満たさない場合 → **ガス合計のみ**を書き込み、給湯・暖房は書き込まない。

#### ⚠️ 旧システムの2つの異常点

##### ① flag 5は給湯ガスが**負**になり得る

flag 5では暖房ガス ＝ `2.0` を固定値として設定し、`給湯 ＝ 合計 − 2.0` として算出する。

しかしflag 5に入る条件は `cost >= 0.3` だけである。そのため合計ガスが `0.3` 〜 `2.0` の間にあると:

| 合計ガス | 暖房ガス | 給湯ガス |
|---|---|---|
| `2.40` | `2.0` | `0.40` ✅ |
| `0.50` | `2.0` | **`−1.50`** ❌ |

コードには書き込み前に**負値をブロックする処理がない** — 負の値がそのままDBに書き込まれる。

さらに定数 `2.0` は**単位の異なる2つの役割**を兼ねている: 閾値 `0.3` を作るための倍数であり、同時にflag 5での**ガス量**そのものでもある。

##### ② 熱源「油」に対応する閾値が無い

| 事象 | 詳細 |
|---|---|
| 分離が許可される条件 | 熱源 ∈ `{1 = 13A, 2 = LPG, 4 = 油}` |
| しかし3つの閾値配列は | **`1` と `2` のみ定義** |
| コードは配列参照前に`4`を除外していない | → **undefined index** → `null` が返る |
| 結果 | PHP 8では null との緩い比較は両辺が bool に変換されるため（false < true）、`cost >= null` は cost の値によらず**常に真**になる（cost=0.0 でも false >= false で真）→ 誤った分岐が選ばれ、Warning のみでエラーにはならない |
