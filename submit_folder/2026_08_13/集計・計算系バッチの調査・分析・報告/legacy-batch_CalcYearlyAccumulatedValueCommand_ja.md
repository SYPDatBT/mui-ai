# 旧バッチ ― CalcYearlyAccumulatedValueCommand（年毎積算値データ算出機能）

## 概要

`CalcYearlyAccumulatedValueCommand`は、旧システム（EMINEL コンシェルジュサーバー）において**月1回**実行されるバッチである。実行の都度、`s_103`にすでに存在する**1か月分**の31個の日カラムを1つの合計値に集約し、その値を`s_104`の対応する年-行の中のちょうど1つの月カラムに書き込む — 対象は10種類の指標（ガス、電気、蓄電池…）。クラス名に「Yearly／年毎」とあるのは、書き込み先テーブル`s_104`が1行＝1年×12個の月カラムという保存単位を持つためであり、これはあくまで保存単位であって、1回の実行あたりの計算単位は月である。

月カラムへの書き込み後、バッチは続けて「再計算」（`recalculation`）と呼ばれるステップを実行する — ただし月次バッチ（`CalcMonthlyAccumulatedValueCommand`）とは異なり、このステップは**抜け落ちた月を遡って探すことはしない**：処理中の当該月のみを再度クエリし、直前に書き込んだ月カラムへ2回目の上書きを行い、その上で`s_103`側の元となった月-行に「集約済み」フラグを立てる。バッチはDBの読み書きのみを行う — 外部API呼び出し、CSVの読み込み／出力、メール送信はいずれも行わない。詳細は第2部を参照。

## 第1部 ― 概要

| 項目 | 内容 |
|---|---|
| **役割** | `s_103`にすでに存在する月ごと31個の日カラムを1か月分の合計値に集約し、`s_104`の年-行の中のちょうど1つの月カラムへ書き込む。対象は10種類の指標（ガス総合／ガス給湯／ガス暖房／消費電力／ガス発電／太陽光発電／買電／売電／蓄電池放電／蓄電池充電）。同時に`s_103`側の元となった月-行を「年へ集約済み」としてマークする。 |
| **Input** | DBの読み込みのみ、**外部API呼び出しなし、CSV読み込みなし**：`t_101`（世帯一覧）＋`s_103`（日別合計、月あたり31カラム、`CalcMonthlyAccumulatedValueCommand`が事前に書き込み済み）。 |
| **Output** | **DBへの書き込みのみ** — 指標種別ごとに1つの月カラムを`s_104`へupsertし、再計算ステップで同じカラムへ2回目の上書きを行う。`s_103`側の元となった月-行の`c009`フラグを更新する。メール送信なし、CSV出力なし。 |
| **処理概要** | 1. `--type`（必須、`AGGREGATION_TYPE_YEARLY`内の値であること — 10種類）と`--yearmonth`（任意、デフォルト＝前月1日）を読み込み、バリデーションを行い、対象の月カラムを算出する。<br>2. 各`type`について：処理対象月に対応する`s_103`の月-行の31個の日カラム（coalesceで0扱い）を合計し、論理削除されていない全世帯について、世帯ごとに1つの合計値と5つのグループ属性を算出する。<br>3. 各世帯について：トランザクションを開始し、`s_104`の対応する年-行へ1つの月カラムをupsertする。<br>4. 書き込みが成功した場合：ステップ2で使用したのと同じ月-行を再度クエリし（他の月は対象にしない）、同じ月カラムを`s_104`へ2回目のupsertを行う。<br>5. `s_103`の当該月-行に`c009 = 2`（集約済み）フラグを立て、commitする；いずれかのステップでエラーが発生した場合は該当世帯についてのみrollbackする。 |

## 第2部 ― 詳細

### 2.1 実行スケジュールとパラメータ

| 項目 | 内容 |
|---|---|
| 実行スケジュール（cron） | `20 5 1 * *` — 月1回、毎月1日午前5時20分 |
| 実行コマンド | `php cake.php CalcYearlyAccumulatedValue --type=<...> [--yearmonth=<...>]` |
| `--type` | 必須 — 複数値をカンマ区切りで指定、各値は`AGGREGATION_TYPE_YEARLY`内であること（10種類、2.2参照） |
| `--yearmonth`のデフォルト | 当月の1日 − 1か月 |
| `--yearmonth`を手動指定する場合 | フォーマットは`yyyy-MM`（正規表現でバリデーション、フォーマット不正の場合は即座に停止） |
| 対象カラム（`s_104`） | `c%03d` ＝ 月 + 10 → 例：1月→`c011`、12月→`c022` |

### 2.2 年次集計対象の10種類の指標（`AGGREGATION_TYPE_YEARLY`）

| `type` | 業務名称 | 説明 |
|---|---|---|
| `GAS_CO_TYPE_CONSUMPTION` (2) | ガス総合消費量 | 世帯のガス消費量合計（暖房＋給湯＋その他使用を含む） |
| `GAS_WATER_HEAT_RATE` (3) | ガス給湯消費量 | 給湯に使用したガス量 |
| `GAS_HEAT_CONSUMPTION` (4) | ガス暖房消費量 | 暖房に使用したガス量 |
| `POWER_CONSUMPTION` (5) | 消費電力量 | 世帯の消費電力量合計 |
| `GAS_POWER` (8) | ガス発電電力量 | ガスコージェネレーション発電機から発電された電力量 |
| `SOLAR_GENERATION` (9) | 太陽光発電電力量 | 太陽光パネルから発電された電力量 |
| `SALE_ELECTRIC` (10) | 売電量 | 系統へ売電した電力量 |
| `BUY_ELECTRIC` (11) | 買電量 | 系統から買電した電力量 |
| `BATTERY_DISCHARGE` (12) | 蓄電池(放電量) | 蓄電池から放電された電力量 |
| `BATTERY_CHARGE` (13) | 蓄電池(充電量) | 蓄電池へ充電された電力量 |

`AGGREGATION_TYPE_MONTHLY`（11種類、`CalcMonthlyAccumulatedValueCommand`の文書を参照）と比較すると、年次リストには`ROOM_TEMP_ADJUST_CNT`（15、温度調整操作回数）のみが含まれていない — この指標は月単位で止まり、年へは集約されない。

### 2.3 `s_103`から月合計を取得し`s_104`の月カラムへ書き込む

各`type`について、`getAggregateValue`関数が1本のSQLを実行する：`t_101`（論理削除されていない世帯を抽出、`c052 IS NULL`）と`s_103`（該当`type`、`room_id = DETECT_LIVING(0)`、処理対象月の月-行で絞り込み）を結合し、31個の日カラム（`c011`〜`c041`、NULLは0扱い）を合計して1つの`TOTAL`カラムとし、世帯の5つのグループ属性（`c012, c042, c015, c016, c024` — 住宅種別、暖房能力、床面積、居住人数、コージェネレーション種別）を付随させる。

`room_id`は`DETECT_LIVING(0)`で固定的に絞り込まれる — 年次リストの10種類すべてが`room_id = 0`を使用し、この段階で部屋を分けている種別は存在しない。

返却された各世帯について、`updateYearlySensorInfo`関数が新しい`ConSensorMonthlyValue`エンティティを1件作成する — キー（世帯コード、種別、room=0、年） — 5つのグループ属性をコピーし、対応する月カラム（`--yearmonth`から算出した`columnName`）に`TOTAL`をセットしたうえで、主キーに基づいて`save()`（upsert）する — 常に新しいエンティティを作成して保存し、既存行を読み込んで修正することはしない。これは同系統のバッチ（時／日／月）がデータを書き込む方式と同じである。このステップでは`s_104`の**`c009`フラグはセットしない**。

### 2.4「再計算」（`recalculation`）ステップ — 処理中のちょうど1か月のみに触れる

2.3で月カラムへの書き込みを行った後、バッチは続けて`recalculation`を呼び出す。これは3つのステップから成る。

```text
1. createUpdateData: s_103を再クエリし、正確に
   （世帯コード、type、room=0、日付＝処理対象月）で絞り込む — 2.3と
   同じ月の条件で、前後の月へは拡張しない。
   → ちょうど1行を返す：（c004＝処理対象月の1日前の日付、TOTAL＝31個の日カラムの合計）
2. updateMonthlySensorRecalculation: 直前に取得したTOTALをそのまま使い、新しい
   ConSensorMonthlyValueエンティティを作成し、フラグc009 = 1をセットし、処理対象の
   月カラム（ステップ1のc004から再計算 — 2.3で書き込んだカラムと一致）にTOTALを
   セットしたうえでsave()（upsert）する — s_104の同じ月カラムへ2回目の上書きを行う。
3. updateRetroactiveFlag: s_103をUPDATEし、c009 = 2（集約済み）をセットする、
   （世帯コード、type、room、日付＝ステップ1で使用したのと同じ月-行）で絞り込む。
```

`CalcMonthlyAccumulatedValueCommand`における同名の仕組み（`NULL`の日を補うために最大1か月前まで遡る）とは異なり、年次バッチの「再計算」ステップは**他のいかなる月へも遡らない** — 上記3ステップはすべて、2.3で処理したばかりの当該月のみを読み書きする。実際の効果としては、ちょうど1つの月カラムへ同じ値をもう1回書き込み、`s_103`側の元となった月-行が年へ集約済みであるとマークすることになる。

2.3のステップ（`updateYearlySensorInfo`）と上記のステップ2（`updateMonthlySensorRecalculation`）は世帯ごとに同じ1つのトランザクション内にある — いずれかのステップでエラーが発生した場合は、その世帯について全体を`rollback()`する。

### 2.5 関連する`s_104`のフィールド

| フィールド | 意味 | いつセットされるか |
|---|---|---|
| `c001`~`c004` | 主キー（世帯コード、機器種別、位置、年） | 書き込みの都度 |
| `c009` | 集約が必要というフラグ | 再計算ステップ（2.4）でのみセット（`= 1`）される；メインの書き込みステップ（2.3）ではこのフラグをセットしない |
| `c111`~`c115` | 5つのグループ属性：住宅種別、暖房能力、床面積、居住人数、コージェネレーション種別 | 世帯一覧から各行へコピー |
| `c011`~`c022` | 月ごとの値を格納する12個のカラム（01月～12月） | 1回の実行につき1カラム — 同じカラムへ2回書き込む（メインステップ2.3＋再計算ステップ2.4） |

### 2.6 関連する業務定数

| 定数 | 値 |
|---|---|
| `AGGREGATION_TYPE_YEARLY` | `[2, 3, 4, 5, 8, 9, 11, 10, 12, 13]` — 業務名称は2.2を参照 |
| `DETECT_LIVING` | `0` — このバッチで絞り込み／書き込みに使用する固定のroom_id |
| 再計算の範囲 | 処理中のちょうど1か月のみ — 遡及を制限する定数は存在しない（遡及しないため） |

### 2.7 集計チェーン

このバッチは、`CalcDailyAccumulatedValueCommand`／`CalcMonthlyAccumulatedValueCommand`の文書で述べた「1行、時間単位ごとにNカラム」というチェーンにおける3番目（最後）の輪である。

```
s_102  "ConSensorHourlyValues"   1行/日   × 24個の時カラム   (CalcDailyAccumulatedValueCommandが書き込み)
   │  CalcMonthlyAccumulatedValueCommand  (1日1回実行)
   ▼
s_103  "ConSensorDailyValues"    1行/月  × 31個の日カラム  (c011~c041)
   │  CalcYearlyAccumulatedValueCommand  (☚ 分析対象のバッチ — 1か月1回実行)
   ▼
s_104  "ConSensorMonthlyValues"  1行/年    × 12個の月カラム (c011~c022)
```

このバッチにおける10種類の指標リストは、`CalcMonthlyAccumulatedValueCommand`が`s_103`へ書き込む11種類の部分集合である（`ROOM_TEMP_ADJUST_CNT`を欠く、2.2参照）。年次バッチには、さらに大きな時間単位へ集計を続けるステップは存在しない — `s_104`がこのチェーンの終点である。
